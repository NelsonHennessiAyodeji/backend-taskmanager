# Task Management REST API

A RESTful backend API for a simple Task Management System. The API allows team members to create, retrieve, filter, update, and delete tasks.

This project was developed as part of a Backend Intern Technical Case Study.

Here is a live version: [https://backend-taskmanager-opew.onrender.com/api/v1/task] for a quick showcase

---

## Features

- Create tasks
- Retrieve all tasks
- Retrieve a single task by ID
- Update existing tasks
- Delete tasks
- Filter tasks by status
- Input validation
- MongoDB database persistence
- Mongoose ODM
- Appropriate HTTP status codes
- Centralized error handling
- Handling of invalid task IDs
- Handling of non-existent task IDs
- Handling of non-existent routes
- RESTful API structure

# Task Object

A task contains the following information:

```json
{
  "id": "task-id",
  "title": "Learn MongoDB",
  "description": "Study MongoDB queries and Mongoose",
  "status": "pending",
  "dueDate": "2026-08-20T18:00:00.000Z",
  "createdAt": "2026-08-13T12:00:00.000Z"
}
```

## Fields

| Field         | Type        | Description                                     |
| ------------- | ----------- | ----------------------------------------------- |
| `id`          | String      | Unique identifier generated by MongoDB/Mongoose |
| `title`       | String      | Task title                                      |
| `description` | String      | Description of the task                         |
| `status`      | String      | Current task status                             |
| `dueDate`     | Date/String | Date and time the task is due                   |
| `createdAt`   | Date        | Date and time the task was created              |

## Status Values

The API supports the following task statuses:

```text
pending
completed
```

New tasks default to:

```text
pending
```

# API Endpoints

| Method   | Endpoint                 | Description              |
| -------- | ------------------------ | ------------------------ |
| `POST`   | `/task`                  | Create a new task        |
| `GET`    | `/task`                  | Retrieve all tasks       |
| `GET`    | `/task?status=pending`   | Retrieve pending tasks   |
| `GET`    | `/task?status=completed` | Retrieve completed tasks |
| `GET`    | `/task/:id`              | Retrieve one task        |
| `PATCH`  | `/task/:id`              | Update a task            |
| `DELETE` | `/task/:id`              | Delete a task            |

# 1. Create a Task

## POST `/task`

Creates a new task.

### Request

```http
POST /task
Content-Type: application/json
```

### Request Body

```json
{
  "title": "Learn MongoDB",
  "description": "Study MongoDB queries and Mongoose",
  "dueDate": "2026-08-20"
}
```

A status can also be supplied:

```json
{
  "title": "Learn MongoDB",
  "description": "Study MongoDB queries and Mongoose",
  "status": "pending",
  "dueDate": "2026-08-20"
}
```

### Successful Response

**201 Created**

```json
{
  "msg": "Created new task",
  "newTask": {
    "id": "...",
    "title": "Learn MongoDB",
    "description": "Study MongoDB queries and Mongoose",
    "status": "pending",
    "dueDate": "2026-08-20",
    "createdAt": "2026-08-13T12:00:00.000Z"
  }
}
```

### Possible Status Codes

| Status | Meaning                   |
| ------ | ------------------------- |
| `201`  | Task successfully created |
| `400`  | Invalid request data      |
| `500`  | Internal server error     |

# 3. Filter Tasks by Status

## GET `/task?status=<status>`

Tasks can be filtered by status using a query parameter.

### Get Pending Tasks

```http
GET /task?status=pending
```

### Get Completed Tasks

```http
GET /task?status=completed
```

The API validates the supplied status before using it as a database filter.

### Invalid Status

For example:

```http
GET /task?status=Invalid
```

The API returns:

**400 Bad Request**

```json
{
  "msg": "Invalid status"
}
```

### Successful Response

**200 OK**

```json
[
  {
    "id": "...",
    "title": "Learn MongoDB",
    "description": "Study MongoDB queries",
    "status": "pending",
    "dueDate": "2026-08-20",
    "createdAt": "2026-08-13T12:00:00.000Z"
```

# 4. Get a Single Task

## GET `/task/:id`

Retrieves a specific task using its MongoDB ID.

### Request

```http
GET /task/64f123456789abcdef123456
```

### Successful Response

**200 OK**

```json
{
  "id": "64f123456789abcdef123456",
  "title": "Learn MongoDB",
  "description": "Study MongoDB queries",
  "status": "pending",
  "dueDate": "2026-08-20",
  "createdAt": "2026-08-13T12:00:00.000Z"
}
```

### Invalid ID

If an invalid MongoDB ID is supplied:

```http
GET /tasks/123
```

the API returns:

**400 Bad Request**

```json
{
  "msg": "Invalid task ID"
}
```

### Non-existent ID

If the ID has a valid MongoDB format but does not correspond to an existing task or the not found handler handles it:

**404 Not Found**

```json
{
  "msg": "Task not found"
}
```

# HTTP Status Codes

The API uses standard HTTP status codes to communicate the result of each request.

| Code  | Meaning               | Usage                                       |
| ----- | --------------------- | ------------------------------------------- |
| `200` | OK                    | Successful GET, PATCH, or DELETE request    |
| `201` | Created               | Successfully created a task                 |
| `400` | Bad Request           | Invalid input, status, or malformed task ID |
| `404` | Not Found             | Requested task or route does not exist      |
| `500` | Internal Server Error | Unexpected server/database error            |

---

# Error Handling

The application uses centralized error-handling middleware so controllers do not need to repeat the same generic error-response logic.

Errors are handled according to their type.

```text
Invalid input
    ↓
400 Bad Request

Invalid MongoDB ID
    ↓
400 Bad Request

Valid ID but task does not exist
    ↓
404 Not Found

Unexpected server/database error
    ↓
500 Internal Server Error
```

A separate fallback route handles requests to endpoints that do not exist.

For example:

```http
GET /something-that-does-not-exist
```

returns:

```json
{
  "msg": "Route not found"
}
```

# Input Validation

Incoming task data is validated on the mogoose layer before being accepted by the database.

Validation includes:

- `title` is required
- `title` has a minimum length
- `title` has a maximum length
- `description` is required
- `status` must be one of the supported values
- `dueDate` must contain a valid date value or a string for simplicity
- Task IDs must be valid MongoDB ObjectIds when used in ID-based endpoints

This prevents malformed data from being stored in the database.

---

# Database

MongoDB is used as the persistent database for the application.

Mongoose is used as the ODM (Object Data Modeling) layer between the Node.js application and MongoDB.

Mongoose provides:

- Schema definitions
- Data validation
- MongoDB model abstraction
- Query functionality
- Automatic timestamps

MongoDB/Mongoose automatically generates a unique `_id` for each document. This identifier is used when retrieving, updating, and deleting individual tasks.

The application does not manually generate task IDs.

The `createdAt` timestamp is also generated automatically through the Mongoose timestamp configuration.

# REST API Design

The API follows REST-oriented conventions.

| HTTP Method | Endpoint     | Purpose                 |
| ----------- | ------------ | ----------------------- |
| `POST`      | `/tasks`     | Create a task           |
| `GET`       | `/tasks`     | Retrieve all tasks      |
| `GET`       | `/tasks/:id` | Retrieve one task       |
| `PATCH`     | `/tasks/:id` | Partially update a task |
| `DELETE`    | `/tasks/:id` | Delete a task           |

Filtering is implemented through query parameters:

```http
GET /task?status=pending
```

Rather than creating separate endpoints such as:

```text
/task/pending
/task/completed
```

This keeps the API flexible and follows common REST API conventions.

# Assumptions

The following assumptions were made during development:

1. A task has two possible statuses: `pending` and `completed`.
2. New tasks default to `pending`.
3. MongoDB/Mongoose generates the unique task ID automatically.
4. `createdAt` is generated automatically by Mongoose timestamps.
5. Task IDs are MongoDB ObjectIds.
6. The API accepts and returns JSON.
7. Filtering is currently supported by task status.
8. Authentication and authorization are outside the scope of this case study because they were not specified in the requirements.
9. A task can be partially updated using the `PATCH` endpoint.
10. Invalid task IDs and valid but non-existent task IDs are treated as different error cases.
11. A live version was provided even though it was not specified: https://backend-taskmanager-opew.onrender.com/api/v1/task

# Challenges Encountered

## Query Parameter Validation

Query parameters received through Express are not automatically typed as the application's domain types.

For example, the `status` query parameter has a broad Express/Node query type rather than automatically being recognized as:

```text
"pending" | "completed"
```

The API therefore validates the supplied value before using it as a MongoDB filter.

---

## MongoDB ID Validation

MongoDB IDs need to be validated before performing database operations.

This allows the API to distinguish between:

- An incorrectly formatted ID
- A correctly formatted ID that does not exist in the database

This results in clearer and more appropriate HTTP responses.

---

## Error Handling

A centralized error-handling middleware was used to keep controllers focused on their primary responsibilities.

Rather than repeating generic error handling in every controller, errors can be passed to a common handler which determines the appropriate HTTP response.

---

## TypeScript Integration

TypeScript was used throughout the application to provide compile-time type checking for controllers, requests, database-related code, and application logic.

This helped catch invalid assumptions and type mismatches during development rather than only at runtime.

# Technical Decisions

## Why TypeScript?

TypeScript was chosen to provide static typing and better maintainability. It also helps identify type-related errors during development before the application is executed.

## Why Express?

Express provides a lightweight and well-established way to build REST APIs with Node.js. It also provides straightforward middleware and routing functionality.

## Why MongoDB?

MongoDB provides a document-oriented data model that maps naturally to the task object used by this application. It also integrates well and FAST with Node.js through Mongoose.

## Why Mongoose?

Mongoose provides schema definitions, validation, models, and convenient database operations while still allowing direct use of MongoDB's document-oriented model.
